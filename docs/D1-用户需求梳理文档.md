## 1. 项目背景与目标

### 1.1 背景

运营方拥有多款客户端软件，需要一套自助式授权系统：向用户发放激活码（K 码），软件在本地验证激活码、联网换取授权信息与运行配置，运营方通过网页后台集中管理软件、卡密、配置与请求日志。运营方更换服务器或域名时，无需重新发布软件，通过"地址转换页"把旧 K 码换成指向新地址的新 K 码即可。

### 1.2 业务目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 一套后台统一管理多个软件的授权 | 软件数量不设硬上限，各自独立配置 |
| G2 | 支持时效型、次数型两种授权 | 每张卡只选一种，规则清晰可核对 |
| G3 | 下发内容不明文、软件端可解密 | 数据库与网络传输中无明文 API Key / 配置 |
| G4 | 换服务器不用重发软件 | 地址转换页可批量/单个重签 K 码 |
| G5 | 运营可追溯 | 每次请求有日志，可统计每张卡的激活与消耗 |
| G6 | 低门槛部署 | 廉价虚拟主机、无 HTTPS 环境即可上线 |

### 1.3 成功标准

- 运营方能在未购买服务器、且主机不提供 HTTPS 的情况下，用最廉价的虚拟主机跑通全流程。
- 客户端软件**只需内置一把通用公钥 A**；每个软件的第二层公钥 B_i 由 K 码携带下发。
- 卡密过期 / 次数耗尽后，软件在联网校验时能被正确拒绝。

## 2. 术语与缩略语

| 术语 | 含义 |
|---|---|
| K 码 | 激活码，第一层加密产物，内含 `card_id`、授权服务器地址、**该软件的公钥 B_i**；软件用内置公钥 A 离线解密 |
| card_id | 卡密唯一标识，通常为卡号 |
| 业务包 | 第二层加密产物，含授权信息与配置；服务器用**该软件的私钥 B_i** 加密下发，软件用 K 码中解出的**公钥 B_i** 解密 |
| 公钥 A / 私钥 A | **全局唯一**的第一层密钥对：私钥 A 只在服务器用于签发/重签 K 码；公钥 A 内置于所有软件，用于离线解 K 码 |
| 公钥 B_i / 私钥 B_i | **每个软件独立一对**的第二层密钥对：私钥 B_i 只在服务器用于加密该软件业务包；公钥 B_i 随该软件的 K 码下发，软件不预置 |
| 授权票据 | 次数型卡每次消费前由服务器签发的一次性/短期凭证（详见 §6.4 扣次规则） |
| 时效型卡 | 只校验到期时间，不扣次数的卡 |
| 次数型卡 | 校验剩余次数，每成功消费一次扣 1 的卡 |
| 设备标识 | 客户端上报的设备唯一标识（由软件自行生成） |
| 软件标识 | 每个软件在后台登记的全局唯一字符串 |

## 4. 使用场景

- **US-1 发卡**：管理员创建软件（系统自动生成该软件独立的 B_i 密钥对）→ 生成一批卡密（时效型或次数型）→ 设置默认配置 → K 码中封装 `card_id` + 服务器地址 + 该软件公钥 B_i → 发给用户。
- **US-2 激活**：用户输入 K 码 → 软件用内置公钥 A 离线解出 `card_id`、服务器地址、公钥 B_i → 带上 `card_id`、软件标识、设备标识请求服务器 → 服务器校验通过后用该软件私钥 B_i 加密业务包下发 → 软件用公钥 B_i 解密，得到授权与配置。
- **US-3 次数消费**：次数型卡每次调用 AI 前向服务器请求一次"授权票据"，服务器原子扣 1 次，票据有效期短；扣完即拒绝。
- **US-4 换服务器**：运营方迁移服务器/域名 → 在地址转换页填入新地址 → 输入旧 K 码 → 系统用私钥 A 解出内容（含公钥 B_i，保持不变）、只替换服务器地址、重新加密输出新 K 码 → 发给用户，软件无需更新。
- **US-5 运维审计**：管理员在日志页按卡号 / 时间 / 软件 / 结果筛选，统计每张卡激活几次、消费几次、扣次前后数量。

## 6. 核心业务规则

### 6.1 授权模式

| 模式 | 校验内容 | 扣次 | 到期/耗尽表现 |
|---|---|---|---|
| 时效型 | 仅校验 `当前时间 <= expire_at` | 否 | 到期后拒绝激活 |
| 次数型 | 校验 `remain > 0` 且卡启用 | 是，每次消费扣 1 | `remain=0` 后拒绝 |

每张卡**只能选一种模式**，创建后模式不可随意切换（切换需作废旧数据，避免规则冲突）。

### 6.2 两层加密流程（v1.1 调整）

**密钥体系**：

| 层 | 密钥 | 范围 | 存放 | 用途 |
|---|---|---|---|---|
| 第一层 K 码 | 私钥 A | 全局唯一 | 仅服务器（Web 根外） | 签发 / 重签 K 码 |
| 第一层 K 码 | 公钥 A | 全局唯一 | 内置所有软件 | 离线解 K 码，得 `card_id` + 地址 + 公钥 B_i |
| 第二层 业务包 | 私钥 B_i | 每软件一对 | 仅服务器（Web 根外） | 加密该软件业务包 |
| 第二层 业务包 | 公钥 B_i | 每软件一对 | 随该软件 K 码下发 | 软件解密业务包 |

**流程**：

1. **第一层（K 码）**：后台用**全局私钥 A** 加密 `card_id + 服务器地址 + 该软件公钥 B_i + 校验字段` 生成 K 码；软件用内置**全局公钥 A** 本地离线解密，一并得到 `card_id`、服务器地址与公钥 B_i。
2. **第二层（业务包）**：软件带 `card_id + 软件标识 + 设备标识` 请求授权地址；服务器查卡识别所属软件，用该软件**私钥 B_i** 加密授权信息与配置下发；软件用 K 码中解出的**公钥 B_i** 解密。
3. **私钥 A、所有私钥 B_i 只存服务器、绝不下发**；软件**只内置一把公钥 A**，各软件公钥 B_i 随 K 码动态下发。

> 为何这样设计：软件无需为每款软件内置不同公钥（只内置通用公钥 A）；第二层密钥按软件隔离，某软件密钥泄露不牵连其他软件；轮换 B_i 后重发该软件 K 码即可，软件内置公钥 A 不用动。

### 6.3 下发内容（每张卡 / 每个软件可单独设置）

| 类型 | 字段 | 是否加密下发 |
|---|---|---|
| 授权信息 | 授权类型、到期时间 / 剩余次数 | 是 |
| AI 配置 | 接口地址、API Key、模型名称 | 是 |
| 自定义文本 | 任意字符串 | 是 |
| JSON 参数 | 任意 JSON 对象 | 是 |

软件解密后**本地直接请求 AI 接口，不经服务器代理**（用户明确决策，见 §11）。

### 6.4 扣次规则

用户定义："只要调用了 AI 就扣一次。" 在直连模式下服务器无法直接观察 AI 调用，故落地为：

- **次数型卡每次消费前，软件向服务器申请一张"授权票据"**（一次轻量 HTTP 请求，不代理 AI 流量）；服务器原子扣 1 次并签发短时效票据。
- 默认严格模式：每次申请票据扣 1；可选宽松模式：票据在有效期内复用不重复扣（需业务确认）。
- 时效型卡不申请票据、不扣次。

> 该规则的安全边界见 §11.2，属于用户已知并接受的权衡。

## 11. 安全边界与已知风险声明（重要）

本节是需求梳理的关键输出，需用户在评审时明确确认"知悉并接受"。

### 11.1 API Key 下发到客户端

- **事实**：软件解密后持有 API Key 并直连 AI 接口。任何能逆向客户端的人，都能按公钥 A 解 K 码、再用其中公钥 B_i 解出业务包里的 API Key。
- **后果**：卡密过期 / 禁用**无法收回已下发的 Key**；次数控制在绕开客户端后失效。
- **用户决策**：接受，并以"每个 API Key 标注可用额度（金额/token）"作为最终成本防线。
- **缓解建议**：① 为不同软件分配独立 Key（与 B_i 按软件隔离的思路一致），便于泄露后单独吊销；② 设置额度硬上限与用量告警；③ 定期轮换 Key 与 B_i；④ Key 权限最小化（限定可用模型）。

### 11.2 扣次无法精确绑定到"真实 AI 调用"

- **事实**：API Key 已下发、AI 直连，服务器不参与 AI 请求，无法确认票据是否真的用于一次 AI 调用，也无法确认一次票据是否被用于多次调用。
- **用户决策**：接受"申请票据即扣 1"作为近似。
- **缓解建议**：票据短时效（如 60 秒）+ 一次性（nonce 服务端去重）；客户端上报调用量与服务端票据数做趋势对账，异常时人工介入。

### 11.3 "私钥加密、公钥解密"的安全边界

- **事实**：私钥加密的数据可用对应公钥解密。公钥 A 内置软件、公钥 B_i 随 K 码下发，均对外公开。因此该方向提供的是**来源认证与防篡改**，**不提供针对逆向者的机密性**。
- **实际收益**：数据库与网络传输中均无明文，防"顺手抓包/拖库直接看到 Key"；中间人无私钥 A/B_i，无法伪造合法 K 码或业务包。
- **不保证**：拿到 K 码的人即可用公钥 A 解出公钥 B_i，进而解开抓到的业务包。故业务包的"机密性"仅在攻击者未同时拿到 K 码与抓包数据时成立。
- **结论**：满足"不明文下发 + 软件可解密"的功能诉求，属轻量级保护，不等同于强机密性系统。

### 11.4 无 HTTPS / 无 SSL 的传输风险（用户已知悉并接受）

- **事实**：全站 HTTP，请求参数（`card_id`、`software_id`、`device_id`、`nonce`、时间戳）明文传输，存在被监听、重放、篡改的可能。
- **尚存的保护**：① 业务包经过加密与完整性校验，中间人无私钥 B_i 无法伪造；② `nonce` + 时间戳 + 服务端去重可挡重放；③ 请求可被监听但其中无 API Key（Key 在加密业务包内）。
- **不保证**：无法防中间人删除/拦截请求、无法防会话 Cookie 被嗅探、无法做域名身份验证。管理后台登录凭据在 HTTP 下明文传输。
- **缓解建议**：① 管理后台尽量放在内网或限制访问 IP；② 会话 Cookie 设 `HttpOnly + SameSite`；③ 关键管理操作二次确认 + 日志；④ 若后续主机支持，优先给管理后台单独开启 HTTPS。
- **用户决策**：按最差条件（无 HTTPS / 无 SSL）设计与部署。

### 11.5 部署形态决策

| 条件 | 选择 |
|---|---|
| 虚拟主机提供 openssl/pdo_mysql/mbstring 扩展、可放 Web 根目录外的目录，**即使无 HTTPS** | 廉价虚拟主机（符合预期，推荐起步） |
| 上述扩展不满足，或需要常驻队列/定时任务/AI 代理 | 轻量云服务器（Nginx + PHP-FPM，可控性高） |

本需求当前全部功能在"PHP 7.2 + MySQL 5.6 + 无 HTTPS"条件下可实现，按此最差环境设计。

## 12. 验收标准

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| AC-01 | 初始化 | 在无 HTTPS 的 PHP 7.2 + MySQL 5.6 环境装完并锁定 |
| AC-02 | 发卡 | K 码能被公钥 A 离线解出正确 `card_id`、地址与该软件公钥 B_i |
| AC-03 | 时效卡 | 未过期放行、过期拒绝，不产生扣次 |
| AC-04 | 次数卡 | 每消费扣 1，扣次前后数量与日志一致，扣完拒绝；并发不超扣 |
| AC-05 | 加密下发 | 数据库与抓包中均无明文 API Key/配置；软件用 K 码内公钥 B_i 解密还原 |
| AC-06 | 密钥隔离 | 不同软件解出的公钥 B_i 不同；某软件私钥 B_i 可单独轮换 |
| AC-07 | 直连 AI | 软件解密后拿到的 AI 配置可用于本地直连 |
| AC-08 | 地址转换 | 旧 K 码转换后新码指向新地址，`card_id` 与公钥 B_i 不变，软件仍可用 |
| AC-09 | 日志 | 每次请求有记录，可按卡统计激活/消费次数 |
| AC-10 | 兼容 | 在 PHP 7.2 + MySQL 5.6 环境跑通全部主流程 |
